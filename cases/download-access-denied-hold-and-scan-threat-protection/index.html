Case 18Web and accessAccess Denied downloads from hold-and-scan threat protection

Downloads blocked by a scan that logged nothing

"Access Denied" on a file export, and the console showed no block at all.

~2.1 swait before the 403
2HARs compared
0events in the obvious view

Symptom

After a malware scanning policy went live, users of a supplier portal got an "Access Denied" page instead of a file from one export endpoint — while a sibling export endpoint kept working. Nothing appeared in the console view the admin was checking.

Investigation

Compared working and failing HAR captures. The failing response carried the proxy's own direct-response header and block-page template with no origin server headers at all — while a favicon request in the very same capture returned genuine origin headers, proving the proxy generated the block rather than the site. Timing was the giveaway: about 2.1 seconds of wait before the 403, meaning the file was fetched from origin first and then blocked.

Root cause

That delay is the signature of hold-and-scan threat protection, not a pre-fetch policy block. One endpoint's generated file was hitting either a false-positive verdict or the unscannable / max-size action, while its sibling passed the same scan.

Fix

Explained the empty console first: these blocks land under alerts and page events, not application events — and size-exceeded or unscannable actions raise no malware alert whatsoever. Then a path forward: reproduce with an exact timestamp, pull page events filtered on user, domain and URL to name the responsible policy and action, and only then choose between a scoped exception, a higher scan-size threshold, or a changed unscannable action.
