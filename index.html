DLP & detection engineering

The national-ID pattern with an 80% noise problem A customer's Aadhaar regex matched nearly every 12-digit number in their traffic. RE2 · DLP
2structural rules exist~80%of 12-digit strings matched12digit target format
Symptom

An Aadhaar (India national ID) detection rule flooded the customer with false positives — order IDs, transaction references, and phone numbers all triggered it.

Investigation

Researched the issuing authority's actual numbering structure: only two rules exist — first digit 2–9, and a Verhoeff checksum as the 12th digit. The middle digits are random, so no regex refinement could ever be selective. The unformatted 12-digit branch matched roughly 80% of all 12-digit strings.

Root cause

Checksum validation needs arithmetic, which no regex can express — and the platform's RE2-style engine additionally rejects lookarounds ((?…) constructs), ruling out boundary tricks.

Fix

Word-boundary-hardened pattern within RE2 limits, layered with the platform's predefined identifier and proximity keywords. Delivered a categorized synthetic test corpus — match, non-match, and boundary cases — so the customer could verify before rollout.

The encrypted file that looked like phone numbers Cipher text kept tripping phone-number detection — and every "fix" regex crashed the compiler. RE2 · DLP
7.89bits/byte entropy{50}fixed quantifier0hits on normal documents
Symptom

A near-random cipher file (7.89 bits/byte entropy) triggered the phone-number rule constantly. The customer wanted a pattern to identify cipher files so they could be excluded.

Investigation

Byte-distribution and entropy analysis, then systematic elimination: negated Unicode classes timed out at DFA compilation, high-byte patterns never matched because the engine strips non-ASCII before scanning, and bounded quantifiers like {150,1024} blew the compile budget — confirmed by a "Regex compilation timed out" error captured in a HAR file.

Root cause

RE2 compiles to a DFA with a strict size budget; large quantifier upper bounds multiply states until compilation fails. The idea was right — the state-machine cost was the problem.

Fix

A fixed-quantifier pattern — [!-~]{50} — matching 50+ consecutive printable non-space characters. Minimal DFA, instant compile, tens of thousands of hits on cipher files, zero on normal documents.

The draft that escaped before the block Blocking the send wasn't enough — the mail client had already saved the content server-side. CASB · HAR
23 MBHAR parsed1endpoint serves every action
Symptom

DLP correctly blocked sensitive webmail sends, but the same content could then be opened as a draft from any unmanaged device — a clean bypass of the control.

Investigation

Parsed a 23 MB HAR capture of a compose session and traced the auto-save behaviour: debounced POSTs persist the draft — subject, body, recipient — to the provider's servers while the user is still typing, long before any send action.

Root cause

The provider routes drafts, sends, archiving, and labeling through one universal sync mutation endpoint. Nothing in the URL distinguishes a draft-save from a send, so a URL-level block would break the entire mail app.

Fix

Content-aware inspection of the POST payload body regardless of draft/send state — plus an honest architectural finding: the residual gap (corporate accounts on unmanaged devices) needs identity-layer controls, not endpoint DLP alone.

Email DLP's return path, rejected by Exchange Inspected mail bounced with "wrong Office 365 region" — the error text was lying. Email DLP
451 4.4.62SMTP rejection code2connectors to reconcile
Symptom

With SMTP Email DLP inline, outbound mail failed with 451 4.4.62 … ATTR35 — "mail sent to the wrong Office 365 region."

Investigation

Traced the full mail flow: Exchange Online hands mail to the DLP proxy correctly; the failure is on the return leg, where the proxy hands inspected mail back for final delivery. The rejection string held the real clue: ValidationStatus of '' is EmptyCertificate.

Root cause

Exchange Online couldn't attribute the returning session to the tenant — the inbound connector wasn't matching the TLS client certificate the proxy presented, so the session was treated as anonymous relay and refused.

Fix

Align the inbound connector's certificate identification with the certificate name the proxy actually presents (verified via SNI in the logs), with the loop-prevention transport rule confirmed in place so inspected mail isn't re-steered infinitely.

Endpoint DLP

Same policy, two PCs, one silent failure An identical print-control policy blocked on one machine and did nothing on another. EPDLP
6enforcement stages traced2machines compared
Symptom

A printer content-control policy with a DLP profile triggered and blocked correctly on one PC but failed silently on a colleague's — same policy, same user group, same printer fleet.

Investigation

Traced the full enforcement chain in system logs on both machines: policy load → directory group resolution → kernel hook interception → PDF spool capture → cloud DLP scan → block action. On the working machine every stage fired; on the broken one, no print job ever reached the interception stage.

Root cause

Print driver architecture. The working PC used a v4 class driver over WSD — a path the endpoint hook intercepts. The failing PC used a vendor v3 universal driver on a direct TCP/IP port, which pushes raw page data past the spool stage the hook captures.

Fix

Re-provision the affected printer on the v4 class driver path, confirming the theory without waiting on another log round — turning "DLP is broken" into a driver-standardization action.

USB devices frozen for exactly 120 seconds Encrypted drives and conferencing devices hung on insert — and every obvious fix targeted the wrong layer. EPDLP · Kernel
120 shold deadline0x102STATUS_TIMEOUT69hold events logged
Symptom

Two separate cases: a USB conferencing device and a hardware-encrypted USB drive whose launcher apps took minutes to start — or never started — with the endpoint agent enabled.

Investigation

Kernel logs showed the launcher volumes marked controlled and frozen, with every file-open held pending a policy verdict that never arrived — each hold expiring at STATUS_TIMEOUT (0x102) after the 120-second deadline. Explained why the admin's device-control allow rules and app-exclusion lists couldn't help: those act on a different enforcement layer than the content-control hold.

Root cause

No content control policy existed at all. With nothing to evaluate held opens against, the policy engine never produced a verdict, so every open on a frozen volume defaulted to the full timeout.

Fix

Create a content control policy covering removable-device activity. The engine then returned prompt safe-to-open verdicts and holds released instantly — reframing a suspected product defect as a configuration gap, with the layer-by-layer reasoning documented for future cases.

Client, steering & performance

The office network that locked itself out Plugging into the corporate LAN killed the internet — a fail-close deadlock with no way back in. Steering
166resolution failures0successful on-prem detections24off-prem detections
Symptom

Users joining the office wired LAN lost all internet access, with the client showing "Disabled due to network change." Cycling through a different Wi-Fi network temporarily cured it.

Investigation

Debug-log forensics: 166 hostname-resolution failures against the geo-load-balancer service, zero successful on-prem detections, PAC auto-detection errors, and fail-close active — cross-referenced into one causal chain.

Root cause

A self-reinforcing deadlock. Egress-IP on-prem detection needs to reach a cloud service over the internet; the office only allows internet via an SSL-inspecting proxy; the client queries that service directly. Detection fails → client assumes off-prem → tunnel can't establish → fail-close blocks all traffic — including the detection traffic that would break the loop.

Fix

Switch on-prem detection to a DNS-based method using an internal-only FQDN — removing the internet dependency entirely — with firewall allowlisting excluded from SSL inspection (required by certificate pinning) as the fallback design.

The 60-second Share button Office's Share dialog crawled for one user — and the obvious suspect turned out to be a lab artifact. DTLS · pcap
59–125 sfirst-byte stalls6tunnel rebuilds per hour1350configured tunnel MTU
Symptom

The Share pane in Excel and other Office apps took 30–60 seconds to load with the client enabled — 3–5 seconds without it. One user affected, a colleague on identical policy unaffected.

Investigation

Lab replication first pointed at the embedded browser control silently upgrading DNS to DNS-over-HTTPS — real behaviour, but I proved it was an artifact of the lab's public-DNS config, not the customer's environment. Production captures told the real story: pooled connections returning zero bytes for 59–125 seconds, repeated DTLS MTU write failures, and six tunnel re-establishments in one hour versus once in 2.5 hours for the healthy user.

Root cause

Zombie connections — the app held pooled flows whose gateway-side state had silently died, a consequence of DTLS/UDP path-MTU fragility, with no session-not-found notification enabled to tell the client.

Fix

Switch the tunnel protocol from DTLS to TLS for a scoped test group — fixing the real root cause with zero loss of inspection coverage, after showing why IP bypasses (too narrow) and process bypasses (coverage sacrifice) were the wrong trades.

Docker push at one-third speed Bypassed traffic was still slow — because three security agents were stacked on one machine. WSL2 · pcap
3inspection agents stacked13 vs 40Mbit/s with vs without
Symptom

Container image pushes from WSL2 to an internal registry took 5–10 minutes with the client enabled — near-instant without — even though the traffic was private-IP bypassed and the process had a cert-pinned bypass rule.

Investigation

Debug logs confirmed the bypass decisions were correct and captures proved the flows never entered the tunnel — so it wasn't steering. A network-state dump then revealed three simultaneous inline inspection products on the host, each with kernel packet drivers; capture analysis pointed at segmentation-offload suppression taxing even bypassed flows.

Root cause

Datapath cost, not policy: bypassed traffic still crosses the kernel driver stack, and with three vendors' filter drivers loaded the per-packet cost compounded — the binary "client on/off" test had unfairly attributed the whole cost to one product.

Fix

An isolation test plan disabling one inspector at a time to find the dominant cost, matching process exclusions across all products (verified against the actual socket-owning process, not the assumed one), and a corrected RCA replacing an earlier no-op recommendation.

The client that wouldn't come back A macOS client died the same week as a major release — but the release was innocent. macOS · NPA
4log files correlated2 minwindow of credential loss95 MBmoved before failure
Symptom

A user's macOS client became fully disabled and unresponsive to re-enable attempts from both the admin console and the endpoint — escalated as a possible regression in a just-shipped golden release.

Investigation

Forensic timeline across four log files: reconstructed the upgrade to the minute, then traced ZTNA tunnel state from healthy (~95 MB transferred) to errored via cert-refresh failures — every credential file returning file-not-found, keychain lookups failing — all starting in one precise two-minute window, days after the upgrade.

Root cause

External deletion of the client's on-disk credential and certificate state plus its keychain items, with the host's third-party EDR remediation as the leading explanation. A later network-interface flapping event killed the coasting tunnel, which had masked the original loss.

Fix

Separated the two failures, cleared the release as a cause, and pinpointed the exact log lines, PIDs, and timestamps behind each conclusion — turning a release-blocking escalation into an endpoint remediation and EDR-exclusion action, plus a cohort grep to formally clear the release group.

The greyed-out icon on a working tunnel The UI said security was off. Traffic said otherwise — and both were telling the truth. VDI · WMI
~19concurrent sessions0x800705afcommit limit reached2symptoms, one cause
Symptom

On a pooled VDI/RDS session host, the client's Internet Security icon greyed out for all users — yet browsing was still steered and policy blocks still enforced, so protection was demonstrably working.

Investigation

Cross-referenced the UI process log against the service log and found host memory commit exhaustion, which had left the system management service unresponsive. That broke the client's ability to read BIOS serial and CPU ID, so it couldn't derive a stable hardware ID — and without it, decryption of the per-user encrypted credential store failed.

Root cause

The UI re-reads that encrypted store on every redraw, so it greyed out; the background service kept its cached tunnel state and carried on steering. One host-level resource problem, two very different symptoms. The registry fallback for hardware ID had been stripped from the VDI image, leaving no backup path.

Fix

Drain and reboot the host as the immediate fix, then commit/page-file sizing work with the platform team for ~19 concurrent sessions — plus a product request for a hardware-ID fallback where the management service is unavailable and the registry value is absent.

The CORS failure that wasn't a steering failure A private app broke on a non-standard port — and everyone assumed the port wasn't published. ZTNA · CORS
3overlapping app definitions found2candidates left standing1command to settle it
Symptom

A BI dashboard published through ZTNA failed to load an embedded forms component, with the browser reporting CORS errors against an API on a non-standard port. The working theory was that the port wasn't published as an app, so traffic was going direct or to the wrong proxy.

Investigation

Decoded the base64-encoded PAC script embedded in the managed browser's policy export and found the host published three times — on 443, on the API port, and a third overlapping definition — all routing to the ZTNA explicit proxy. The HAR then showed the preflight requests on that port carrying the injected ZTNA auth headers and returning genuine 200s, proving they reached a real backend.

Root cause

Not steering. The browser and client layers were exonerated outright, leaving exactly two candidates, both server-side of the proxy: the data path answering the preflight itself or altering the Origin header before the backend saw it, or the backend's own CORS allow-list missing the app origin.

Fix

Rather than guess between them, I defined the decisive test — run the preflight from the publisher host straight at the backend, bypassing the gateway — which separates the two in a single command. Also flagged the duplicate app definitions for cleanup, while noting first-PAC-match-wins meant they caused no functional harm here.

The bank login that demanded SMS every time The bank's domains were bypassed correctly — but the login broke anyway. SSL · HAR
2HAR captures compared1uncovered third-party domain
Symptom

Users logging into a US regional bank's portal were forced into SMS step-up verification whenever the client was enabled — despite an existing bypass covering all the bank's own domains.

Investigation

Compared working and failing HAR captures from the same user and device: the failing session received an explicit step-up challenge from the auth API. Debug logs showed the bank's domains correctly bypassed — while the third-party device-fingerprinting service the login depends on was being tunneled through the proxy.

Root cause

Split egress: the device fingerprint and the auth request reached the bank from different public IPs, so its risk engine flagged every session as untrusted and demanded step-up.

Fix

Extend the bypass to the fingerprinting domains, with verification defined up front: confirm the new bypass entries appear in the debug log and the step-up challenge disappears from fresh captures.

Device management sync that bypassed the wrong domain The customer followed the vendor doc exactly — and bypassed a domain the flow never touches. SSL bypass
0x80190194404 on device check-in1wrong domain bypassed
Symptom

MDM device sync failed with 0x80190194 (404) on protected endpoints, even though the customer had already added the authentication endpoint named in the vendor's documentation to their steering exception list.

Investigation

Read the actual failing request in the device's reported management server address — it targets the device gateway, not the authentication domain that had been bypassed. That domain only serves consumer account sign-in, so bypassing it changed nothing for this flow.

Root cause

Device check-in authenticates with the MDM device certificate over mutual TLS. When the proxy decrypts the session it terminates TLS and cannot present the device's client certificate, so the request arrives unauthenticated and the gateway answers 404. The vendor explicitly does not support inspection on these endpoints.

Fix

Bypass the device-management and device-gateway domain families from SSL inspection using wildcards, since subdomains are involved — with the vendor's own endpoint documentation cited so the customer could take the change through their approval process.

The one where the answer was "it isn't us" Webmail failed in the normal browser profile, worked in incognito — with the client on in both. HAR · SSO
11 MBHAR parsed18 vs 1identity headers sent vs answered
Symptom

A user couldn't load corporate webmail in their normal browser profile, but the same account worked immediately in an incognito window — with the security client active in both cases, which pointed suspicion straight at the proxy.

Investigation

Parsed an 11 MB HAR of the failing session: interactive sign-in succeeded, but the passive single-sign-on handoff aborted and bounced to the account chooser, and a cross-service session endpoint returned 400. The browser's identity-consistency request header appeared on 18 requests with only one matching response — a clear session-state mismatch. Proving the block page works, without any malware Validating threat controls end to end using only harmless, industry-standard test artifacts. IPS · Validation
2test vectors0real malware used
Requirement

Verify that a tenant's IPS/threat notification page actually renders for users after enabling the feature — mimicking command-and-control and intrusion traffic without touching real malware or standing up a real C2 server.

Investigation

Separated two things that get conflated: rendering the user-facing block page versus generating a backend alert. Response-side signatures raise alerts but won't necessarily produce a block page, so a single test can pass while the thing you care about goes unverified.

Approach

A layered plan: the industry-standard harmless anti-malware test file to exercise the block page on download, and a safe public NIDS test endpoint over plain HTTP to generate alerts — the plaintext path deliberately isolating whether SSL decryption is itself the problem.

Outcome

A repeatable validation runbook with the exact console views for confirming each result, so the customer could evidence coverage rather than assume it.

Downloads blocked by a scan that logged nothing "Access Denied" on a file export, and the console showed no block at all. Threat Protection
~2.1 swait before the 4032HARs compared0events in the obvious view
Symptom

After a malware scanning policy went live, users of a supplier portal got an "Access Denied" page instead of a file from one export endpoint — while a sibling export endpoint kept working. Nothing appeared in the console view the admin was checking.

Investigation

Compared working and failing HAR captures. The failing response carried the proxy's own direct-response header and block-page template with no origin server headers at all — while a favicon request in the very same capture returned genuine origin headers, proving the proxy generated the block rather than the site. Timing was the giveaway: about 2.1 seconds of wait before the 403, meaning the file was fetched from origin first and then blocked.

Root cause

That delay is the signature of hold-and-scan threat protection, not a pre-fetch policy block. One endpoint's generated file was hitting either a false-positive verdict or the unscannable / max-size action, while its sibling passed the same scan.

Fix

Explained the empty console first: these blocks land under alerts and page events, not application events — and size-exceeded or unscannable actions raise no malware alert whatsoever. Then a path forward: reproduce with an exact timestamp, pull page events filtered on user, domain and URL to name the responsible policy and action, and only then choose between a scoped exception, a higher scan-size threshold, or a changed unscannable action.

Blocking one feature without blocking the app Stop users wiring corporate data sources into a public AI assistant — but leave the assistant usable. CASB · Policy
2HARs, mine and the customer's3endpoint families mapped2policy layers designed
Requirement

A customer wanted to stop users connecting third-party data sources to a public AI assistant, without blocking the assistant itself — so a blunt domain block was off the table from the start.

Investigation

Parsed two HAR captures: my own replication, plus the customer's, which captured the full end-to-end flow my replication had missed. Between them I mapped three distinct endpoint families — the OAuth initiation call, the callback that completes a connection, and the runtime endpoint that proxies live connector traffic.

Design

A two-layer URL policy: a surgical block on initiation and callback to prevent new connections, plus defense-in-depth on the runtime and directory paths to neutralise existing ones. Organisation IDs and connector UUIDs sit inside the URL paths, so every rule needed wildcard matching to survive real traffic.

Fix

Delivered the rule set with two findings that saved effort: third-party OAuth provider domains need no individual blocking once initiation is cut at the assistant's own domain, and admin-side governance on the vendor's enterprise plan would be a more durable control than network blocking alone — worth raising with the customer rather than quietly selling them a policy.

Getting a new desktop app through the stack Mapping exactly what an app needs on the wire, before it becomes a ticket. Enablement
443TCP for everything normal3478UDP for voice media0inbound ports required
Requirement

Determine the full network footprint of a desktop AI client so it could be allowed through proxy and firewall policy cleanly, rather than debugged after rollout.

Findings

Everything is outbound only — no inbound listeners. Normal traffic and streaming both ride TCP 443, with streaming needing the WebSocket upgrade handshake permitted rather than just the port opened. Voice prefers UDP 3478 and falls back to 443, so quality complaints usually trace to the UDP path being closed rather than the app misbehaving.

The gotchas

Two things break this app specifically under a security stack. Its desktop build validates certificates strictly, so SSL inspection produces a certificate error and forces users back to the web version — the vendor's guidance is a decryption bypass for their domains. And sign-in hands off to the default browser and receives the OAuth callback on a loopback address, so host firewalls that block loopback break login in a way that looks nothing like a network problem.

Outcome

A ready-to-apply allowlist covering the app's own domains plus its static-asset, upload, and telemetry dependencies — turning a likely run of confusing tickets into one configuration change.
