  1. The problem

    After a customer turned on Email DLP, outgoing emails started bouncing with an error saying the mail was sent to the wrong Office 365 region.

    What I found

    The error message was misleading. Emails reached Netskope and were checked without trouble. The failure happened on the way back: when the checked email was handed back to Microsoft, Microsoft could not tell which company it came from, so it refused it.

    The fix

    Update the customer's Microsoft 365 connector so it recognises the certificate Netskope presents when it hands mail back.

    Symptom

    With Email DLP inline over SMTP, outbound mail failed with 451 4.4.62 and a message claiming the mail was sent to the wrong Office 365 region.

    Investigation

    Traced the full mail flow. Exchange Online handed mail to the DLP proxy correctly; the failure was on the return leg, where inspected mail is handed back for final delivery. The rejection text held the real clue: ValidationStatus of '' is EmptyCertificate.

    Root cause

    Exchange Online couldn't attribute the returning session to the tenant. The inbound connector wasn't matching the TLS client certificate the proxy presented, so the session was treated as anonymous relay and refused.

    Fix

    Align the inbound connector's certificate identification with the certificate name the proxy actually presents (confirmed from the SNI in the logs), and confirm the loop-prevention transport rule so inspected mail isn't routed back for inspection again.

  2. The problem

    A DLP rule meant to catch Aadhaar numbers, India's national ID, kept flagging order numbers, invoice references and phone numbers.

    What I found

    Aadhaar numbers have almost no fixed pattern. Apart from the first digit, they look like any other 12-digit number, so the rule matched about 80% of all of them. The only real check is a checksum, and a text pattern cannot do that maths.

    The fix

    Use Netskope's built-in Aadhaar detector, require a nearby word such as 'Aadhaar' before the rule fires, and tighten the pattern's edges. I also gave the customer a set of test numbers to check the rule before going live.

    Symptom

    An Aadhaar detection rule flooded the customer with false positives: order IDs, transaction references and phone numbers all triggered it.

    Investigation

    Checked the issuing authority's numbering structure. Only two rules exist: the first digit is 2 to 9, and the 12th digit is a Verhoeff checksum. The middle digits are random, so the unformatted 12-digit branch matched roughly 80% of all 12-digit strings.

    Root cause

    Checksum validation needs arithmetic, which no regex can express, and the RE2 engine also rejects lookarounds, which rules out boundary tricks.

    Fix

    A boundary-hardened pattern within RE2 limits, layered with the platform's predefined identifier and proximity keywords, plus a categorised synthetic test set (match, non-match and boundary cases) so the customer could verify before rollout.

  3. The problem

    With Endpoint DLP turned on, a USB meeting device and an encrypted USB drive took minutes to open their apps, or didn't open them at all.

    What I found

    Before letting each file on the device open, the laptop waited for a policy decision. No decision ever came, so every file waited the full 120 seconds before timing out. The settings the admin had already changed were the wrong ones for this.

    The fix

    The customer had no content control policy at all, so there was nothing to make a decision with. Once one was created, answers came back instantly and both devices worked normally.

    Symptom

    A USB conferencing device and a hardware-encrypted USB drive took minutes to start their launcher apps, or never started them, with the endpoint agent enabled.

    Investigation

    The endpoint logs showed every file-open on those USB volumes held while waiting for a policy verdict, each timing out after 120 seconds (STATUS_TIMEOUT). The admin's device-control allow rules and app exclusions couldn't help, because they act on a different enforcement layer.

    Root cause

    No content control policy existed. With nothing to evaluate the held file-opens against, no verdict was ever produced, so every open waited for the full timeout.

    Fix

    Create a content control policy covering removable-device activity. Verdicts then came back immediately and the holds released instantly: a configuration gap, not a fault.

  4. The problem

    A customer wanted staff to keep using a public AI assistant, but stop them connecting it to other apps such as email or file storage. Blocking the whole assistant was not an option.

    What I found

    Connecting an app happens in three steps, each with its own web address: starting the connection, finishing it, and using it afterwards.

    The fix

    URL rules that block the first two steps, so no new connections can be made, and the third, so old connections stop working. The rest of the assistant keeps working as normal.

    Requirement

    Stop users connecting third-party data sources to a public AI assistant without blocking the assistant itself, so a blunt domain block was ruled out.

    Investigation

    Analysed two HAR captures and mapped three endpoint families: the OAuth initiation call, the callback that completes a connection, and the runtime endpoint that carries live connector traffic.

    Design

    A two-layer URL policy: block initiation and callback to stop new connections, and block the runtime paths to neutralise existing ones. Organisation and connector IDs sit inside the URL paths, so every rule needed wildcard matching.

    Fix

    Delivered the rule set, noting that third-party OAuth provider domains need no individual blocking once initiation is cut, and that admin-side governance in the vendor's enterprise plan would be a more durable control than network blocking alone.

    CASBOAuthURL policy
    3 steps in connecting an app

  5. The problem

    Company laptops could not sync with Microsoft Intune. The customer had already added the address from Microsoft's guide to their exception list.

    What I found

    That address wasn't used for syncing at all. Sync goes to a different set of Microsoft addresses, and the laptop proves who it is with its own certificate. When that traffic was inspected, the certificate couldn't get through, so Microsoft rejected the request.

    The fix

    Stop inspecting Microsoft's device-management addresses. Microsoft's own documentation says these must not be inspected, which made the change easy for the customer to approve.

    Symptom

    Intune device sync failed with 0x80190194 (HTTP 404), although the authentication endpoint named in the vendor's documentation was already in the steering exception list.

    Investigation

    Read the device's management server address: sync targets the device gateway, not the authentication domain that had been excepted. That domain only serves account sign-in, so excepting it changed nothing for this flow.

    Root cause

    Device check-in authenticates with the device certificate over mutual TLS. When the proxy decrypts the session it terminates TLS and can't present the device's client certificate, so the request arrives unauthenticated and the gateway returns 404. Microsoft does not support inspection of these endpoints.

    Fix

    Exclude the device-management and device-gateway domain families from SSL inspection with wildcards, citing Microsoft's endpoint documentation so the customer could take the change through approval.

    SSL inspectionmTLSIntune
    404 error on every sync

  6. The problem

    A news website opened through Remote Browser Isolation got stuck on a 'verifying your browser' page. The customer also wanted to switch off the site's chat feature.

    What I found

    My first guess was wrong. The browser recordings showed the website's own hosting service was limiting visits from shared internet addresses, and it did this even without isolation involved.

    The fix

    The lasting fix is on the website's side: allow the customer's Netskope addresses. For the chat, I found the exact address to block, and warned that one connection must stay open because it also carries the live news feed.

    Symptom

    Users opening a market-news site through Remote Browser Isolation in read-only mode were stuck on a 'verifying your browser' page, and the customer also wanted the site's chat disabled.

    Investigation

    My first read, a JavaScript challenge conflicting with read-only mode, was wrong. The HAR captures showed the challenge came from the site's hosting edge: its mitigation header, an HTTP 429 and proof-of-work assets, firing even without isolation in the request chain.

    Root cause

    The hosting edge rate-limits by source IP, and shared proxy egress addresses tripped it three minutes after a clean session from the same machine. Not an isolation problem.

    Fix

    Allow-listing the customer's egress addresses on the site side as the lasting fix. For the chat, I identified the exact API endpoint to block, and flagged the WebSocket that must stay open because it also carries the live market feed.

  7. The problem

    After a malware scanning policy went live, users got 'Access Denied' when exporting one file from a supplier portal. The admin couldn't find any block in the console.

    What I found

    The browser recording showed the block page came from Netskope, after a two-second pause. That pause means the file was downloaded and scanned first, then blocked. Scan blocks are recorded in a different part of the console from normal policy blocks, which is why the admin saw nothing.

    The fix

    Reproduce the download at a known time, look in page events and alerts to find which rule fired, then choose the smallest change: an exception for that trusted portal, or a higher file-size limit.

    Symptom

    After a malware scanning policy went live, one export endpoint on a supplier portal returned 'Access Denied' while a sibling endpoint kept working, and the console view the admin was checking showed nothing.

    Investigation

    Compared working and failing HAR captures. The failing response carried the proxy's block-page headers and no origin server headers, while another request in the same capture returned genuine origin headers. About 2.1 seconds passed before the 403, so the file was fetched first and then blocked.

    Root cause

    That delay is the signature of scan-then-block threat protection, not a policy block. One endpoint's generated file was hitting a malware verdict or a scan size or unscannable-file action, while its sibling passed.

    Fix

    These blocks are recorded under alerts and page events rather than application events. Reproduce with an exact timestamp, filter page events on user, domain and URL to name the policy and action, then choose between a scoped exception, a higher scan-size limit or a changed unscannable action.

  8. The problem

    A server logged 15 failed SSH logins from one internal address, and the customer wanted to know which user it was.

    What I found

    That address belonged to the Netskope connector that reaches private apps on users' behalf, so the server only ever sees the connector. Netskope records who connected; the server records whether the password was right. You need both.

    The fix

    Match the times of the failed logins with Netskope's connection records for that server. The user on those five short connections is the answer, and the pattern looked like an automated job still using an old password.

    Symptom

    A security team saw 15 failed SSH logins on an internal file-transfer server, all from one internal IP, and asked which user was responsible.

    Investigation

    That IP was the private-access publisher, which opens connections to the application on the user's behalf, so the server only ever sees the publisher. The SSH account name has no link to the platform identity, and network events showed Allow because the verdict is on the connection, not the login inside it.

    Root cause

    Nothing was wrong with private access. Five distinct source ports meant five connections, and each failed attempt writes three lines to the server's auth log: fifteen events, five attempts.

    Fix

    Correlate the five connection times with network events for that destination; the user field on those short, low-byte sessions is the answer. The pattern pointed most likely to an automated transfer job with an expired service-account password.

  9. The problem

    An internal app on a custom port worked on the office network, but sign-in failed when users opened it in Netskope Enterprise Browser.

    What I found

    After sign-in, the app checks that the reply comes back to the exact address it expects, including the port number. Through the browser, the request arrived without the port number, so the check failed.

    The fix

    Set the app's server to always use its real port number. In the longer term, move the app to the standard port 443 so this can't happen again.

    Symptom

    An internal service-desk application on a non-standard port worked through the private-access client, but through the enterprise browser its SAML sign-in ended in an authentication error.

    Investigation

    Traced the SAML flow in the HAR. The identity-provider leg was clean; the failure came when the assertion returned to the application.

    Root cause

    The application builds its expected reply URL from the host and port it receives. On the browser access path the request arrived without the custom port, so the assertion's destination no longer matched.

    Fix

    Pin the port in the application server's connector configuration so it reports the right port whatever the host header says, with a rolling restart. Longer term, move the app to 443.

  10. The problem

    When laptops plugged into the office network, the internet stopped completely. Switching to another Wi-Fi and back fixed it for a while.

    What I found

    To know whether it's in the office, the Netskope client checks something online. In this office the internet only works through the company proxy, and the check didn't use it. So the check failed, the client assumed it was outside the office, couldn't connect, and then blocked everything, including the check that would have fixed it.

    The fix

    Detect the office with a simple internal DNS name that only works inside the office. No internet is needed, so the loop can't happen.

    Symptom

    Users joining the office wired network lost all internet access, with the client reporting it was disabled due to a network change. Switching to another network cured it for a while.

    Investigation

    Debug-log analysis found 166 name-resolution failures against the gateway-selection service, zero successful office detections, proxy auto-detection errors and fail-close active, which together formed one causal chain.

    Root cause

    A self-reinforcing deadlock. Egress-IP office detection needs to reach a cloud service; the office only allows internet through an SSL-inspecting proxy, which the client doesn't use for that check. Detection fails, the client assumes it's off-site, the tunnel can't form, and fail-close blocks everything, including the check that would break the loop.

    Fix

    Switch office detection to DNS-based detection with an internal-only FQDN, removing the internet dependency entirely. Firewall allow-listing, excluded from SSL inspection, is the fallback design.

  11. The problem

    Macs downloaded the Netskope client through the JAMF management tool, then the installation failed every time.

    What I found

    The install script needs the company's own Netskope address. It had been given only the general Netskope domain, so the installer couldn't find the company's settings, kept retrying, and ran out of time.

    The fix

    Put the full company address into the script, check the settings file it creates, and clean up the half-installed Macs before trying again.

    Symptom

    A JAMF policy downloaded the client onto Macs and then reported the installation as failed, every time.

    Investigation

    Read the JAMF log and the macOS install log side by side. The install-parameters file generated by the script was first invalid JSON, later valid JSON with no usable tenant hostname, so the installer couldn't fetch its enrolment configuration and kept retrying.

    Root cause

    The script's tenant parameter held the shared service domain instead of the tenant-specific hostname. The retry loop then ran the post-install step past the macOS installer's 600-second limit, turning a configuration error into a hard failure.

    Fix

    Set the full tenant hostname from the admin console, confirm the token parameters, validate the generated JSON before re-running, and clean up the half-installed state from earlier attempts.

  12. The problem

    Another company's secure-connection app stopped working whenever Netskope was turned on.

    What I found

    An exception already existed, but only for that app's error-reporting address. Its real connections went to many other addresses and were still being sent through Netskope.

    The fix

    Add an exception for the other app's program itself, so all of its traffic goes direct whatever address it uses, and confirm with the security team that this traffic won't be inspected.

    Symptom

    Users couldn't connect another vendor's secure-access client while ours was enabled; disabling ours fixed it immediately.

    Investigation

    Grouped the client log by process. The other client's service dominated the traffic, and an exception existed only for its error-reporting host. Its tunnel, DNS and edge connections were still being steered to our proxy.

    Root cause

    A domain exception on the wrong host. The connections that mattered went to anycast addresses the exception never covered.

    Fix

    A process exception for the other client's service executables, or its predefined certificate-pinned app entry, backed by destination ranges where needed, with a note to the policy owner that this traffic then leaves uninspected.
